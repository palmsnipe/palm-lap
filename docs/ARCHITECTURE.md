# Architecture and development notes

## Data path

```text
Palm OS 5
  LAP UUID 0x1102 / RFCOMM channel 4
  PPP client
       |
       v
BlueZ 5.82 (pairing, SDP, RFCOMM listener)
       |
       | Unix file descriptor via org.bluez.Profile1.NewConnection
       v
palm-lapd -> pppd 2.5.2 -> plap10 (10.77.0.1 <-> 10.77.0.10)
       |
       v
nftables filter + masquerade -> eth0 -> 192.168.1.0/24 / Internet

Palm WebPro -> 10.77.0.1:53 dnsmasq -> 192.168.1.1 DNS
Palm WebPro -> 10.77.0.1:8080 palm-web -> managed PRC/PDB store
Mac browser -> 192.168.1.50:8080/admin -> auth/CSRF -> validated helper

Paired/trusted Bluetooth device -> OBEX Object Push -> BlueZ obexd
  -> org.bluez.obex.Agent1 -> separate audited Bluetooth inbox
```

The withdrawn protocol stops at the RFCOMM/PPP boundary. BlueZ, D-Bus, Python 3, pppd, kernel PPP, nftables, and systemd are current Debian 13 components.

## Components

### `palm-lapd`

`/usr/local/libexec/palm-lapd` exports two D-Bus objects:

- `/org/palmlap/profile`, interface `org.bluez.Profile1`;
- `/org/palmlap/agent`, interface `org.bluez.Agent1`.

It registers `00001102-0000-1000-8000-00805f9b34fb` using an explicit SDP record containing:

- service class `0x1102` (LAN Access Using PPP);
- public browse group `0x1002`;
- protocol stack L2CAP `0x0100` -> RFCOMM `0x0003`, channel 4;
- profile descriptor LAP `0x1102`, version 1.0;
- English/UTF-8 language-base descriptor and service name `Palm LAP`, so Palm's LAN Setup can display a name instead of “Unnamed Network Access Point.”

The record matches the fields generated by the historical BlueZ `sdptool add LAN` implementation, but it is registered through BlueZ 5's maintained Profile API. The old daemon/tools are not installed or run.

BlueZ is asked to require cryptographic link-key authentication. BlueZ 5.82's
additional external-profile `RequireAuthorization` path is disabled because it
reproducibly stalled an authenticated, encrypted Palm TX RFCOMM connection for
about 25 seconds without calling the registered agent. This does not remove the
gateway's service authorization boundary: `NewConnection` checks the MAC
against the configured allowlist before taking ownership of BlueZ's RFCOMM file
descriptor or starting PPP. It then maps the MAC to its static peer IP and
connects the descriptor to `pppd` stdin/stdout using pppd's `notty` mode.

`AuthorizeService` remains implemented defensively for BlueZ paths that invoke
it, but the authoritative and tested check is `NewConnection`; unauthorized
devices cannot create a PPP session even if they are separately bonded.

Child sessions run in their own process groups. BlueZ disconnection, daemon shutdown, and child exit are handled explicitly. The daemon never logs the PIN or data payload.

### Pairing agent and window

The same daemon is BlueZ's default `KeyboardDisplay` agent so it can answer Bluetooth 1.1/1.2 legacy `RequestPinCode` as well as newer passkey requests. Every pairing callback checks `/run/palm-lap/pairing.json` and its expiry. With no live state, requests are rejected.

`palm-lap-pair open`:

1. prompts for a temporary PIN;
2. creates the state file as root mode `0600`;
3. sets BlueZ pairable/discoverable timeouts to 600 seconds;
4. enables pairing and discovery;
5. starts `palm-lap-pairing-close.timer`.

The timer or a manual close disables both adapter flags and deletes the state. On every daemon start, the controller is explicitly closed unless a non-expired window exists. This addresses BlueZ enabling pairability when a default agent is registered.

Closing pairing also explicitly leaves BlueZ's writable `Connectable` property enabled. Otherwise BlueZ disables classic page scanning when both Pairable and Discoverable become false, preventing a bonded Palm from reconnecting.

### Classic discovery class compatibility

The Bluetooth SIG class for this gateway is a LAN/Network Access Point with the Networking service bit. `/etc/bluetooth/main.conf` sets major/minor class `0x000300`. BlueZ dynamically supplies service bits, but BlueZ 5.82's `get_uuid_mask()` maps PAN and DUN to Networking and omits withdrawn LAP UUID `0x1102`; only the unrelated SIM Access plugin therefore contributed Telephony, producing `0x400300` (and originally Miscellaneous before the major-class fix).

At every `palm-lap-pair open`, the helper uses BlueZ's current management tool to reassert LAN/AP major/minor class and add LAP UUID with Networking service hint `2`. The on-air class becomes `0x420300`:

An enabled `palm-lap-compat.service` oneshot performs the same operation after
a short boot-time settling delay. This is necessary because controller reset
clears the management hint and BlueZ still does not infer it from withdrawn LAP.
The pairing helper continues to reassert it immediately before discovery.

- `0x020000` Networking service;
- `0x400000` Telephony service contributed by the installed SIM Access profile;
- `0x000300` LAN/Network Access Point major class.

This matters because legacy Palm discovery can filter inquiry results by Class of Device before it performs SDP. The helper applies the hint immediately before enabling discovery, avoiding any dependency on deprecated BlueZ daemons or utilities.

### PPP

Global `/etc/ppp/options` on this host enables `auth`, `crtscts`, `lock`, and `modem`. `/etc/ppp/peers/palm-lap` deliberately overrides these with `noauth`, `nocrtscts`, `nolock`, and `local`, which are appropriate for an already authenticated Bluetooth stream rather than a physical modem TTY.

The daemon supplies `local:peer`, `ifname`, and up to two `ms-dns` values. IPv6 is disabled on the Palm link because Palm OS 5 is an IPv4 client. Debug logging remains enabled for the pilot; remove `debug` after interoperability stabilizes if log volume is undesirable.

### Routing and firewall

`/etc/sysctl.d/90-palm-lap-forwarding.conf` enables IPv4 forwarding. `/etc/nftables.d/palm-lap.nft` adds base chains after the original Debian accept-policy chains, so its Palm-specific drops still apply without changing unrelated host traffic.

Policy for `plap*`:

- reject source addresses outside `10.77.0.0/24`;
- permit Palm-initiated forwarding only through `eth0`;
- permit only established/related return forwarding;
- reject unsolicited forwarding toward a Palm;
- allow DNS, the Palm file catalog on TCP 8080, and limited ICMP to the Pi's PPP
  address, then block other Pi-local services;
- masquerade the Palm subnet when it leaves `eth0`.

NAT makes outbound LAN/Internet access independent of router changes. For true inbound LAN reachability, add a router route for `10.77.0.0/24 via 192.168.1.50` and redesign NAT/filter policy deliberately.

### DNS compatibility

IPCP advertises `10.77.0.1`, not the off-subnet LAN router, as both Palm DNS
addresses. dnsmasq 2.91 binds dynamically to `plap*`, provides caching only,
and forwards to `192.168.1.1`. DHCP is disabled. This was introduced after
packet counters showed WebPro timing out despite an off-subnet query/reply
crossing NAT; directly connected DNS resolved the incompatibility.

### Web catalog and administration

Waitress serves the Flask application on TCP 8080. `/` and `/files/` are
intentionally compatible with old Palm HTML and return Palm MIME attachments.
`/admin` is passwordless by user choice but restricted to configured LAN source
networks with CSRF-protected POST forms. Palm PPP clients receive 404.

The service is `palmweb`, not `operator` or root. Its sudoers entry permits only
`palm-web-admin`; the helper validates a bounded JSON request and dispatches to
existing pairing/device tools. Bluetooth sends are constrained to the managed
store and executed as `operator` to reach that account's BlueZ OBEX user bus. One
worker serializes transfers. See `WEB-INTERFACE.md` for the complete threat
boundary and operations.

Incoming Object Push uses the operator's current BlueZ `obexd` user service and
the repository's `palm-obex-inbox` Agent1 implementation. The OBEX daemon is
explicitly rooted at `/var/lib/palm-web/inbox`; its filesystem driver otherwise
rejects an agent-selected path outside its configured root. On authorization, the
agent reads `Transfer1.Session`, then uses `Session1.Destination` to identify the
remote address. It accepts only devices whose system-bus `Device1` properties
are paired and trusted. It chooses a collision-safe path in the dedicated inbox,
records a metadata sidecar, and watches `Transfer1.Status` until completion.
Completed files are mode `0640`; the setgid inbox is owned by
`operator:palmweb`, allowing the receiver to create payloads and the LAN-only
web service to read or delete them. The directory is not part of the public Palm
catalog or outbound-send allowlist.

Controller recovery remains bounded. The web helper can restart known services
and can start only the fixed `palm-bluetooth-recover.service` oneshot unit. That
root unit validates `serial0-0` and `hci_uart_bcm`, performs the sysfs
unbind/rebind outside the web service's hardened namespace, and restores power,
connectability, and LAP. Discovery-only class/UUID hints are reapplied by the
pairing helper before a future pairing window rather than during fresh firmware
settling. No arbitrary service name, command, device, driver, or sysfs path is
accepted from HTTP.

## Configuration invariants

- Every device key is a normalized uppercase Bluetooth MAC.
- Every peer address belongs to `subnet`, differs from `local_ip`, and is unique.
- RFCOMM channel is in 1–30.
- At most two IPv4 DNS addresses are passed to pppd.
- Only bonded devices should be placed in the allowlist; the helper enforces this.
- Runtime and repository copies are separate. Edit `src/` or `config/`, review,
  then install deliberately into `/usr/local` or `/etc`; editing the clone does
  not change the running service.

## Future development priorities

1. Remove pilot PPP debug logging after stability.
2. Test simultaneous sessions before declaring multi-device support stable.
3. Add automated tests for configuration, allocation, pairing expiry, web auth,
   upload validation, and job-state transitions.
4. Put LAN administration behind a separate HTTPS reverse proxy if the LAN is
   no longer fully trusted; keep Palm HTTP isolated on the PPP address.
5. Package the files as a small Debian package if the deployment is replicated.
6. Keep any HTTP/TLS translation service outside `palm-lapd`.
